# Ornith 1.5 Q4_K_M versus deployed Qwen precision

**Decision: retain Qwen precision.** Ornith's substantial speed advantage
and matching small-suite scores did not carry through to reliable native
OpenCode use. Qwen was restored persistently and passed a fresh native
control against the same documents that exposed Ornith's failures.

## Measured results

| Measurement | Qwen precision | Ornith Q4_K_M |
| --- | ---: | ---: |
| Warm short decode, median of six cached probes | 71.665 tok/s | 229.94 tok/s |
| Warm streamed-text TTFT, median of those probes | 65 ms | 39 ms |
| Generated-code contracts, seven tasks × three seeds | 21/21 | 21/21 |
| Nested tool round trips, three × three seeds | 9/9 | 9/9 |
| Repair-agent fixtures v2, two × three seeds | 6/6 | 6/6 |
| Total wall time for the 21 coding cases | 461.24 s | 270.51 s |
| Initial single ~253K prompt plus answer | 208.51 s | 47.20 s |
| Two independent ~253K prompts, slower request completion | 414.24 s | 109.72 s |
| Resume first history after that pair | 2.32 s | 0.86 s |
| Oversized-context rejection and recovery | Pass | Pass |
| Native OpenCode read-only sessions, two batches | 6/6 | **3/6** |

Short decode was about **3.2× faster**, short paired aggregate throughput
was 324.86 versus 111.26 tok/s, and the paired long workload finished about
3.8× sooner. Longer reasoning reduces the realized coding-task speedup:
the 21 generated-code tasks completed about 1.7× sooner, not 3.2×.
Both long-pair runs observed two active slots but zero overlapping streamed
output: prompt processing stalled the other request's decode. These results
do not mean two full-context agents both decode continuously at short-prompt speed.
Initial single-context Ornith probes used CPU vision; the final repeated
and paired-context runs used GPU vision. Sampled GPU use was 29450 MiB for
Qwen and 26062 MiB for GPU-vision Ornith; these snapshots are **not** peak-VRAM
measurements.

## Why promotion was declined

`scripts/check-native-concurrency` ran real OpenCode 1.19.5 sessions through
the deployed LiteLLM aliases. It requires a successful `read` tool and the
requested document's first heading. The prompt and grader were unchanged.

- Qwen initially passed all three sessions (`qwen38-precision-20261105-native.json`).
- Ornith passed ALPHA and GAMMA but reported the model-profile subheading
  `Selection: Ornith-1.5-35B-A3B Q4_K_M` instead of the first heading
  `Default coding-agent profile` (`ornith15-deployed-20261105-native.json`).
- Repeating without changing the task reproduced BETA's heading error;
  GAMMA additionally attempted `/home/user/opencode/ai-station/docs/*`, a
  nonexistent working-tree location, and its external-directory permission
  request was auto-rejected (`ornith15-deployed-20261105-native-repeat1.json`).
- After restoring Qwen, all three sessions passed against the **same updated
  documents** (`qwen38-precision-20261105-native-control.json`).

This is a small native sample, not an estimate of general task failure rate.
It is nevertheless an observed regression in the target agent workflow, so
speed alone was insufficient to replace Qwen. Final selection is
`precision`, Qwen Q4 weights, two fixed 262144-token slots, GPU vision.
Model aliases, 262144 client context, and 16384 output cap are retained.
The restored Qwen also passed tool-error recovery and local image inference
(`qwen38-precision-20261105-restored-history.jsonl`). Final `make profile-status`
matched the selected profile to the live model/arguments. Backend, gateway
and WebUI were active; the alternative GPU backend and candidate were stopped.

## Deployment compatibility findings

The original embedded Ornith template duplicated inline `<think>` history
when `reasoning_content` metadata was also supplied. A temporary deployed
trial failed the existing runtime history-normalization assertion. Qwen was
restored while a minimal fix was prepared.

`scripts/download-ornith-template` now downloads the upstream template at
`10fbf86fed7ecee4a061f8b499a618f46001cac1`, verifies its SHA-256, adds only
inline-history normalization and a version comment, and checks a separate
patched-output hash. Both hashes and the revision are locked in
`config/chat-templates.lock.yaml`. Normal user/assistant renders were checked
to be identical before/after the patch; duplicate inline/metadata history
retains its sentinel once. The real minja renderer then passed the existing
history checks. The model comparison above used the embedded template;
native deployed probes used the history-fixed template.

With `ornith1.5-history-v1`, deployed alias streaming/tool round trips,
reasoning history, request-local budget, configured low/medium ceilings,
tool-error recovery and local GPU image inference all passed. Raw outputs:
`ornith15-deployed-20261105-{aliases,budgets,history}.jsonl`.
Passing these API-level checks did not resolve the native task failures.
The tiny 32-token budget probe checks budget closure and final-answer
presence, not answer correctness; its arithmetic answer was incorrect.

Ornith remains a downloaded **experimental** profile, not the default:
`make profile-ornith` explicitly selects it; `make profile-precision`
returns to Qwen. Switching validates hashes/units, snapshots the old
configuration, restarts the backend/gateway and smoke-tests inference.
Family-specific template keys prevent a later switch from retaining the
other model's template. The selected-model downloader follows the profile.

## Reproducibility

Run on Brain's RTX 5090 (32607 MiB reported VRAM). The baseline was checked
with `make profile-status`: **Qwen3.8-27B UD-Q4_K_XL, precision**, two fixed
262144-token slots. It was not the Q3/three-slot capacity profile.

Both use the pinned llama.cpp b11960 image from `config/images.lock.yaml`,
full GPU model offload, Q4 K/V, `--no-kv-unified`, aggregate context 524288,
two slots, and `--cache-ram 16384`. This RAM cache stores reusable prompt
states; it does **not** substitute for active GPU KV capacity.

Ornith artifacts and SHA-256 checksums are in `config/candidates.lock.yaml`:
repository `ornith-ai/Ornith-1.5-35B-A3B-GGUF`, revision
`12393612fd4f730ff5aadc23e9b8f9648aa49ceb`,
`Ornith-1.5-35B-Q4_K_M.gguf` and `mmproj-Ornith-1.5-35B-BF16.gguf`.
The comparison used Ornith's embedded Jinja template; Qwen used the pinned production
froggeric template. The initial Ornith runs used a CPU-resident projector;
the final three-seed/concurrency runs use GPU vision to match Qwen precision.
These are text tests and do not establish vision quality parity.
Unused `reasoning_effort`/`preserve_thinking` template kwargs must not be
interpreted as supported soft-effort controls in Ornith's embedded template.

## Procedure

1. Download on Brain with `bash scripts/download-ornith-candidate`; both
   artifact hashes must pass before mounting a GPU candidate.
2. `scripts/benchmark-coder` initially ran with 8192 total output tokens and
   8192 thinking-budget tokens, seed 42, `--preserve-thinking --extended`,
   contexts `32000,122000,154000,253000`. Full raw results:
   `qwen38-precision-20261105.json`, `ornith15-q4-k-m-20261105.json`.
3. Ornith exhausted the total-output limit on SSE parsing and retry-delay
   generation. A 16384-token retest (the deployed client output allowance),
   still with an 8192 thinking ceiling, passed both. This diagnostic run is
   `ornith15-q4-k-m-16k-20261105.json`.
4. The final short suite uses **three seeds (42, 43, 44)** and 16384 total
   output tokens for both models. It includes seven coding contracts,
   including a Greek-language task; three nested-tool round trips per seed;
   and three streaming measurements per seed. Files are named
   `{qwen38-precision,ornith15-q4-k-m}-16k-20261105-seed{42,43,44}.json`.
   Thinking sampling is temperature 1.0, top-p .95, top-k 20; nonthinking
   streaming/context sampling is .7/.8/20, presence penalty 1.5. There is no
   MTP or speculative helper. The harness supplies identical request settings.
5. `scripts/benchmark-coder-concurrency` runs three short single/pair repeats,
   reasoning/tool history, simultaneous independent 253K-token contexts,
   cache reuse, oversized-context rejection, and recovery. Its `*-screen`,
   `*-full`, and `*-limit.jsonl` outputs retain timings and answers.
6. The same wrapper runs `scripts/benchmark-agent-repair`: two small English/
   Greek repair fixtures at three seeds, with read/write/test tools, a
   deliberately transient failed write, preserved assistant history, and
   independent final verification. Generated Python runs in a CPU-only,
   memory/CPU-constrained disposable benchmark container. These are fixture
   agent loops, **not** SWE-bench or real-repository completion scores.
   The final `*-agent-repair-v2.json` harness exposes read-only tests and
   returns their source with failed test results, matching a coding agent's
   ability to inspect local failures. Earlier `*-agent-repair.json` runs are
   diagnostics: the first harness rejected missing-file reads outright; a
   second supplied opaque assertion failures without readable tests. Ornith
   repeatedly misclassified `/v10` as an existing `/v1` suffix in the latter.
   Those scaffold versions are not compared against v2. Both models must use
   the identical v2 harness for the final comparison (16384 total output
   tokens, 6144 thinking-budget tokens, temperature 1.0, top-p .95, top-k 20).

The candidate controller stops the active deployed GPU backend, runs Ornith
on the private container network, and restores the previously active backend
on exit. It holds the existing concurrency-controller lock. No client ports
are published for the candidate.

```bash
# On Brain; finish downloads first and run between other inference tasks.
bash scripts/benchmark-coder-repeats http://llama-coder:8000 qwen38-precision-16k-20261105
bash scripts/benchmark-coder-concurrency http://llama-coder:8000 qwen38-precision-20261105
bash scripts/evaluate-ornith-candidate --repeats
```

The current candidate runner uses the history-fixed external template. To
reproduce the original embedded-template comparison exactly, omit its
`--chat-template-file` argument; keep all other recorded settings identical.

The initial long-context needles are deliberately simple. Short repeated
coding checks and repair fixtures cannot establish broad coding-quality
superiority. Promotion requires useful speed gains without observed coding,
tool/history, context-capacity, or deployed API regressions.
